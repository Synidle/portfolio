Digital Ghost Gate was made as my assessment submission for a JavaScript module in university, in which I had to create a 2D RPG-style game using the P5.js library. My game achieved a grade of 92, being recognised for its "highly complex item trading quest and battle system, in addition to a variety of maps and dialogue". Development took about a month, and I made every part of the game myself.

Design

My aim was to create a game that encouraged exploration and engagement through its features and mechanics, despite only encapsulating a small world.

Gameplay is explorative, involving completion of quests, engagement with characters, and the recruitment of "ghosts" are the proxies used for battle in this game.

Ghosts offer complexity to combat, having different spells that can inflict different beneficial or harmful effects upon targets. Moreover, ghosts can have affinities or weaknesses to different elements or damage types. The ghost system was heavily inspired by the persona system in, e.g., Persona 3 (Atlus, 2006), but with the difference of the ghosts being real characters in the world who can be friend or foe and conversed with — so making the world more interesting for exploration.

The most interesting feature is the negotiation mechanic in combat, which allows for multiple solutions to encounters, and encourages exploration and interaction.

A complex conditional dialogue system was also designed to facilitate quests and enrich interactions with characters within the world.

Implementation

That the game was developed entirely in JavaScript, without use of a game engine, offered particular challenges.

My solution to game maps was to have each map a text file, with an integer value corresponding to different tiles. My solution is efficient as I did not need to store tile data, only needing an array of texture references with indices corresponding to those in the map file. Whether a tile had collision was implied according to whether the index was odd or even. Then functionally, tiles are represented as 0 for floor, 1 for walls.

Maps are lodaed via a Scene, which also holds GameObjects and connexions between scenes. Battles are types of Scene, containing arrays for player and opponent ghosts in the battle.

The implementation of the conditional dialogue system was a challenge. My Dialogue class contains an array of text that displays under a condition (a function returning a Boolean value) and can execute a function on completion and can link to another Dialogue object.

The DialogueChoice class inherits from Dialogue, and as such can be used in place of standard Dialogue lines, but facilitates a binary option within dialogue. It could be rewritten to use array parameters in order to offer an indeterminate number of choices, but the retro aesthetic of the game imposes limitations upon the AI and as such I limit dialogue choices to usually just "yes" and "no", with additional decisions made through the player's actions in the game.

Battles utilise a state machine, with the state determining the outcome whenever the player inputs.

Selecting options is facilitated by the callback of my custmo UI classes.

The Battle scene delivers the functions of all actions.

The effect and impact of spells is determined by both the caster and recipients of the spell. First, the damage to be dealt is determined by the caster's stats.

Then, the actual effect is determined by the recipient according to their affinities.

Whether a consequential status effect of a spell is received depends upon stats and randomness.

Whether an attack is evaded altogether is determined by attack's accuracy and a degree of randomness.

But it is ensured spells cast to allies will always be received, and so their effects; a spell that must land can be given an accuracy of 101.

Status effects simply use the existing spell system, but are applied as unavoidable spells once effective.

Stats are receptive to temporary modification by spells; having a separate map for a stat's value to return to allows modifying a value in the stats map.

All of a ghost's status effects are applied recursively using i as the index of the ghost and j as the index of the effect. Recursion was used rather than a for loop because dialogue appears as indication of every effect applied, and dialogue awaits input before progressing.
